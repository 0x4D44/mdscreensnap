# Coverage Report - 2026.01.03

## Executive Summary
The project `mdscreensnap` currently has 86 passing tests. The test suite primarily covers argument parsing, filename generation/sanitization, and PowerShell script generation.

However, the core application logic within the `run` function and the platform-specific execution paths (Windows/WSL command execution) remain largely uncovered. The current tests for `run` only exercise the "dry-run" path.

## Coverage Gaps

### 1. Main Execution Logic (`run` function)
The `run` function (lines 104-171) has significant gaps.
-   **Covered:** Argument parsing, output directory creation (partial), dry-run early exit.
-   **Uncovered (Lines 133-168):**
    -   Delay logic (`std::thread::sleep`).
    -   Screenshot capture invocation.
    -   Clipboard operations.
    -   File saving verification.
    -   "Open after save" logic.
    -   Temporary file cleanup (no-save mode).

### 2. Platform Specific Implementations
The functions that interact with the OS are almost entirely uncovered because they execute shell commands directly.
-   `capture_screenshot_windows_with_monitor` / `capture_screenshot_wsl_with_monitor`: 0% coverage.
-   `copy_to_clipboard_windows` / `copy_to_clipboard_wsl`: 0% coverage.
-   `list_monitors_windows` / `list_monitors_wsl`: 0% coverage.
-   `wsl_to_windows_path`: 0% coverage.

### 3. Environment Detection
-   `is_wsl`: Partially covered.
-   `check_wsl_interop_exists`: Uncovered (reads filesystem).

## Root Cause Analysis
The low coverage in logical areas is due to hard-coded dependencies on side-effect-heavy system APIs:
-   `std::process::Command`: Makes it impossible to unit test command execution without actually running commands (which is slow, flaky, and platform-dependent).
-   `std::fs`: Direct file system calls make isolation difficult.
-   `std::thread::sleep`: Makes tests slow if actually executed.

## Recommendations
To achieve >98% coverage, the application must be refactored to use **Dependency Injection**. We need to abstract the "World" (FS, Time, Process Execution) behind a trait interface. This will allow us to inject a `MockWorld` during testing to:
1.  Verify that `Command`s are constructed with expected arguments.
2.  Simulate file system successes/failures.
3.  Fast-forward time instead of sleeping.
4.  Verify that specific side effects (like opening a file) were requested.
